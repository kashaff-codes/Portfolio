QUEST 1 · HACKATHON · SEP 2026

Occuris Echo

57/57 test cases with 0 silent failures. With the rules switched off, the same agent makes 3.

Problem: For someone with a tremor or low vision, replying to a doctor, booking it and telling family is three apps and about 40 clicks. An agent can do it in one sentence, but they can't easily check what it did. What I built: A voice agent across Gmail, Calendar, Slack and Sheets. Rules settle the request first, Claude only fills gaps, it asks instead of guessing, and nothing irreversible goes out without a yes.
PythonFastAPIClaudeGoogle + Slack APIs
Loom demo Repo
Case study · 1 min read

Decisions

  • Rules before the model. Claude only extracts mentions; resolving them still goes through the rules, so a model mistake becomes a question, not an action.
  • The spoken read-back is built only from what each app reported, never from what the user said. Partial failures are stated: "Slack failed, nothing went out there."
  • "What's waiting for a yes" is computed from the ledger (requested minus completed), never stored as a flag. A crash loses nothing.
  • No vector memory. Nothing here needed similarity search, and it would have added a failure mode I couldn't measure.
  • Tests check the state of in-memory copies of all four apps (emails sent, events created), never what the agent claims it did.

Trade-offs

  • "At 2" means 2 pm for hours 1 to 7. It's a heuristic, so Echo says the time back and the user can catch it.
  • The ledger lives in Google Sheets so users can read and edit their own memory, at the cost of a real database.
  • The parser is English-only; anything off-script falls to the model and is tagged as such.

What I'd do differently

  • Run speech recognition on the device. The browser sends audio to the cloud, which isn't acceptable for medical appointments.
  • Test with disabled users. It's designed to WCAG 2.2, but designed isn't the same as tested.
QUEST 2 · OPEN SOURCE · OCT 2026

Supabase Lite Conformance Kit

Traced 48 failures to 22 root causes and fixed two upstream: passing cases 33 → 36, silent wrong data 15 → 12.

Problem: Supabase Lite (SQLite) only works if apps written for Supabase (Postgres) behave the same on it. Its own tests check SQLite against itself, so they can't catch "Postgres would have returned something different." What I built: A kit that sends the same 81 supabase-js calls to both, diffs the answers and ranks every difference, silent wrong data first, with each cause traced to the line of PostgREST (Haskell) or GoTrue (Go) source that defines the correct behaviour.
TypeScriptPostgreSQLSQLiteGo · Haskell (source)GitHub Actions
Live report Loom walkthrough Repo Upstream PR
Case study · 1 min read

Decisions

  • Black-box only: the kit talks HTTP through supabase-js, so any Supabase-compatible server can be tested by changing a URL.
  • One seed file generates the data for both databases, and CI fails if the generated files are stale.
  • No LLMs and no randomness in verdicts. Every version is pinned, so anyone can reproduce a run.
  • Severity ranks silent wrong data first and declared gaps last, because the silent ones are what hurt users.
  • Failures are grouped by root cause, so the report shows how many distinct problems exist, not just how many cases failed.

Trade-offs

  • No compatibility percentage. A single number would hide which differences matter.
  • Error messages are never compared, only codes. Messages change between versions; codes are the contract.
  • Differences don't fail the build, because they're the output. A --fail-on S1 flag lets a project gate on them.

What I'd do differently

  • Turn the upgrade checks into a real export-to-Postgres migration. Today each value is written to both sides and compared, which isn't the same as migrating.
QUEST 3 · EVAL-FIRST RAG AGENT

supabase-ai-eval

Caught an index silently wrecking recall: one wrong result at 0.18 similarity became five, led by the right one at 0.69.

Problem: A RAG agent's answers look fine until you measure them. I wanted every run scored, stored and visible. What I built: A RAG agent over the Supabase docs with hybrid vector and keyword search, served to other agents as MCP tools. An LLM judge scores every query, and a live dashboard reads the results from Postgres.
PythonpgvectorFastMCPClaude
Live dashboard Repo
Case study · 1 min read

Decisions

  • Replaced an ivfflat index with HNSW. With 100 lists over 12 rows and one probe, every search read a single list, which looked like a weak model, not an index problem.
  • Merged vector and keyword results by rank, not score. Cosine similarity runs 0 to 1 and text rank is unbounded, so blending scores means inventing a scale.
  • Errors are scored separately from failures. When one query hit a DNS error, the harness refused to call that run a valid quality signal.
  • A schema-drift check, because the embedding size is declared in three places that can't check each other, and a mismatch fails quietly.

Trade-offs

  • Six documents and eight test queries: enough to catch real bugs, not a benchmark.
  • An LLM judge is itself a model. Its scores are logged with its reasoning so they can be checked.

What I'd do differently

  • Grow the corpus and the test set together. The one real failure (file uploads) was a gap in the docs I ingested, not in retrieval, and the eval was right to separate the two.

ZONE 2 · RULES OF PLAY

How I work

Three rules I build by.

I assume the AI is wrong until a test says otherwise.

So every agent I ship comes with a known-answer test set. My preprint shows the method on my own pipeline.

When the rules can't decide, the agent asks. It doesn't guess.

One question costs a second. A confident wrong answer costs trust.

Anything that can't be undone waits for a person to say yes.

Emails, messages, purchase orders: a person approves first.
